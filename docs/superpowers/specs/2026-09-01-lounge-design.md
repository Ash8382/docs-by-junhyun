# 쉼터(Lounge) 설계

2026-09-01

## 1. 개요

멍 때릴 때, AI 에이전트가 도는 걸 기다릴 때 들어와서 머무는 실시간 멀티플레이어 공간.
닉네임만 정하면 입장하고, 방향키로 캐릭터를 움직이고, 같은 시간에 들어온 다른 사람이
화면에 보인다. 탑다운 2D 픽셀 뷰.

기존 `/playground`의 다섯 데모는 "구경하는 것"이다. 쉼터는 "머무는 곳"이라는 점에서
성격이 다르고, 그래서 playground 하위가 아니라 별도 경로를 쓴다.

이 프로젝트는 두 가지 목표를 동시에 만족해야 한다.

- **제품**: 혼자 들어와도 심심하지 않고, 둘 이상이면 더 좋은 공간
- **역량**: 실시간 게임 서버를 직접 설계·배포·운영한 경험과, 그것을 설명할 수 있는 근거

두 번째 목표 때문에 관리형 실시간 서비스(Ably, Supabase Realtime)를 쓰지 않고
WebSocket 서버를 직접 만든다. 단순 릴레이 서버는 관리형 서비스를 붙인 것과 설명할
거리가 다르지 않으므로, 서버 권위 상태·클라이언트 예측·보간·델타 인코딩·레이트리밋을
실제로 구현하고 그 효과를 측정한다.

### 비목표

- 경쟁 요소, 점수, 랭킹
- 로그인, 계정, 영구 프로필
- 채팅 로그 보관
- 모바일 터치 조작 (1차 범위 밖. 데스크톱 키보드·마우스 전제)
- 여러 개의 방 / 방 생성

## 2. 사용자 경험

### 입장

`/lounge` 접속 → 닉네임 입력 폼 → 입장. 계정도 비밀번호도 없다.
닉네임은 2~10자, 한글·영문·숫자만. 브라우저에 세션 토큰을 저장해서 재접속하면
같은 아바타로 돌아온다.

화면 하단에 `지금 N명 · 누적 N명`을 항상 표시한다.

### 조작

| 입력 | 동작 |
|---|---|
| `↑↓←→` / `WASD` | 이동 |
| 좌클릭 | 그 지점으로 걸어감. 벽에 닿으면 미끄러짐 |
| 우클릭 | 조사 — 오브젝트면 설명, 빈 바닥이면 3초짜리 마커 |
| `Space` | 앞에 있는 오브젝트와 상호작용 |
| `Enter` | 말풍선 입력창 열기 |
| `1`~`4` | 이모트 |
| `Esc` | 입력창 닫기 |
| `F3` | 디버그 오버레이 (ping, 보간 지연, msg/s, 스냅샷 크기) |

### 방 안의 것들

혼자 있어도 할 게 있어야 한다. 오브젝트는 상태를 서버가 갖는 것과 클라이언트에만
있는 것으로 나뉜다. 이 구분이 서버를 작게 유지한다.

| 오브젝트 | 상호작용 | 상태 위치 |
|---|---|---|
| 📻 라디오 | 오늘의 AI Daily 헤드라인이 흘러나옴 | 서버 (10분 캐시) |
| 🔥 모닥불 | 앉기. 앉은 사람이 늘면 불이 커짐 | 서버 |
| 🤖 NPC | 말 걸면 오늘 기사 한 줄. 파이프라인이 도는 새벽엔 바쁘게 움직임 | 서버 |
| 📚 책장 | 블로그 글 한 편 추천, 누르면 이동 | 클라이언트 (`posts.ts`) |
| 🪴 화분 | 누르면 자람 | 클라이언트 (`localStorage`) |

라디오와 NPC가 쓰는 AI Daily 데이터는 게임 서버가 기존 `/api/ai-daily`를 10분마다
폴링해서 캐시한다. **VPS에 Neon 접속 정보를 두지 않기 위해서다.**

### 빈 방 대책 — 잔상

개인 블로그의 실시간 공간은 기본 상태가 "접속 1명"이다. 그래서 최근 몇 시간 안에
다녀간 사람들의 이동 경로를 반투명 회색 유령으로 재생한다.

**좌표만 저장하고 닉네임·말풍선은 저장하지 않는다.** 휘발성 채팅 원칙을 깨지 않으면서
사람이 다녀간 흔적만 남기는 선이다.

## 3. 아키텍처

```
[Vercel]                          [Oracle Cloud 서울 VPS]
 Next.js /lounge                    Caddy (TLS 자동 발급)
  Canvas 2D 렌더                          │
  입력 → 서버 전송         ── WSS ──▶     ▼
  로컬 예측 + 원격 보간              Node + ws (Docker)
                                     20Hz 시뮬레이션
                                     10Hz 스냅샷 송출
                                     NPC · 잔상 · 레이트리밋
                                          │
                                       SQLite
                                          
                                     ↑ 10분마다 폴링
                    https://docs-by-junhyun.vercel.app/api/ai-daily
```

관리형 실시간 서비스를 쓸 때 필요했던 우회 장치들이 서버 권위 모델에서는 사라진다.
presence는 서버의 `Map` 하나이고, NPC는 tick에서 그냥 움직이면 되며(결정론 트릭 불필요),
잔상은 서버가 이미 모든 경로를 알고 있고, 채팅 필터와 쿨다운은 한 곳에서 처리된다.
그 결과 Next는 정적 껍데기가 되고 `/api/lounge/*` 라우트가 하나도 필요 없다.

### 호스팅 이식성

Oracle은 2026년 6월 15일 Always Free ARM 한도를 4 OCPU/24GB에서 2 OCPU/12GB로
공지 없이 축소했고 8월 18일부터 초과 인스턴스를 자동 종료했다. 무료 티어에 의존하는
이상 같은 일이 또 생길 수 있다.

따라서 **서버는 단일 Docker 컨테이너로 만들고, 호스트에 의존하는 설정은 환경변수로만
받는다.** Oracle이 막히면 Fly.io(월 약 $2)로 옮기는 데 재작성이 필요 없어야 한다.
디스크 의존은 SQLite 파일 하나뿐이므로 볼륨만 옮기면 된다.

## 4. 저장소 구조

**서버와 클라이언트가 같은 타입과 같은 물리 코드를 공유하는 것이 핵심이다.**

공유 방법은 npm workspaces가 아니라 **tsconfig 경로 별칭**(`@shared/*` → `./shared/*`)을
쓴다. workspaces로 묶으면 Next가 TS 소스인 워크스페이스 패키지를 소비하기 위해
`transpilePackages` 설정이 추가로 필요하고 빌드가 깨지기 쉽다. `shared/`를 프로젝트
안의 평범한 TS 파일로 두면 Next는 아무 설정 없이 컴파일하고, 서버는 이미 devDependency로
있는 `tsx`가 같은 별칭을 해석한다. 2단계 Docker 빌드에서는 `shared/`와 `server/`,
루트 `tsconfig.json`만 복사하면 된다.

```
shared/
  protocol.ts    메시지 타입 정의. 서버·클라가 같은 것을 import
  world.ts       타일맵, 충돌 격자, 오브젝트 배치 (순수 데이터)
  physics.ts     이동·충돌 판정 (양쪽에서 같은 코드가 돌아야 예측이 성립)
  constants.ts   tick rate, 속도, 각종 상한

server/
  index.ts       진입점, 설정 로드
  room.ts        tick 루프, 플레이어 Map, 스냅샷 델타 생성
  net.ts         소켓 수명주기, 레이트리밋, 백프레셔, 세션 복구
  npc.ts         NPC 이동과 대사
  traces.ts      잔상 기록·조회
  feed.ts        AI Daily 폴링 캐시
  db.ts          SQLite
  metrics.ts     /metrics 엔드포인트
  Dockerfile

src/app/lounge/
  page.tsx           서버 컴포넌트 (정적)
  LoungeClient.tsx   닉네임 게이트 ↔ 방 전환

src/components/lounge/
  NicknameGate.tsx
  DebugOverlay.tsx

src/lib/lounge/
  engine.ts      입력 수집, 예측, 보간, 로컬 상태
  render.ts      Canvas 그리기 (engine 상태를 받기만)
  net.ts         WebSocket 클라이언트 (engine을 모름)
  interactions.ts 클라이언트 로컬 오브젝트 (책장, 화분)
```

`engine.ts`는 DOM을 모르고 `net.ts`는 `engine`을 모른다. 덕분에 이동·충돌은 순수
함수로 단위 테스트가 되고, 서버 없이도 방이 돌아가서 1단계를 독립적으로 완성할 수 있다.

`physics.ts`를 공유하는 것이 클라이언트 예측이 성립하는 조건이다. 클라이언트가 예측한
위치와 서버 계산이 갈리면 캐릭터가 튄다.

## 5. 프로토콜

**클라이언트는 자기 위치를 보내지 않는다. 의도만 보낸다.** 위치는 서버가 정한다.

좌클릭의 `{x, y}`는 "내가 여기 있다"가 아니라 "저기로 가고 싶다"는 목표 지점이다.
서버는 이 값이 맵 범위 안이고 벽이 아닌지 검증한 뒤 목표로 삼고, 실제 이동은
서버가 자기 tick에서 계산한다. 목표가 유효하지 않으면 무시한다.

### 클라이언트 → 서버

| 메시지 | 내용 |
|---|---|
| `hello` | `{nick, sessionToken?}` — 접속 직후 1회 |
| `input` | `{seq, dir, moving}` — 입력이 바뀔 때만. `dir`은 8방향 |
| `click` | `{seq, x, y}` — 이동 목표 지점 (서버가 검증) |
| `say` | `{text}` — 최대 40자 |
| `emote` | `{id}` — `wave` `sit` `sleep` `think` 중 하나 |
| `interact` | `{objectId}` |

### 서버 → 클라이언트

| 메시지 | 내용 |
|---|---|
| `welcome` | `{playerId, sessionToken, spawn, totalVisitors, traces}` |
| `snapshot` | `{tick, ack, players[]}` — **변경된 플레이어만** |
| `join` / `leave` | `{playerId, nick, color}` |
| `say` / `emote` | `{playerId, ...}` |
| `npc` | `{x, y, line?}` |
| `error` | `{code, message}` |

`ack`는 서버가 처리한 마지막 입력 `seq`다. 클라이언트는 그 이후의 입력만 다시
적용해서 예측 위치를 보정한다(reconciliation).

### 인코딩

1~2단계는 JSON. 3단계에서 `snapshot`만 `ArrayBuffer`로 바꾼다.
좌표는 픽셀 단위 `int16`, 방향은 3비트로 패킹한다.
**전환 전후의 바이트/초를 측정해서 기록으로 남긴다.**

## 6. 서버 설계

### 상수 (`shared/constants.ts`)

서버와 클라이언트가 같은 값을 써야 예측이 맞는다. 한 곳에만 둔다.

| 이름 | 값 |
|---|---|
| `TILE` | 32 px |
| `MAP` | 40 × 30 타일 (1280 × 960 px) |
| `SPEED` | 96 px/s (초당 3타일) |
| `SIM_HZ` | 20 |
| `SNAPSHOT_HZ` | 10 |
| `INTERP_DELAY` | 100 ms |
| `REJOIN_GRACE` | 20 s |

### 틱과 스냅샷

- 시뮬레이션 **20Hz** (50ms 고정 스텝)
- 스냅샷 송출 **10Hz** (100ms)
- 접속자가 0명이면 tick을 멈춘다 (CPU 낭비 방지)

시뮬레이션을 송출보다 빠르게 도는 이유는 입력 처리 지연을 줄이면서 대역폭은
송출 주기로 따로 통제하기 위해서다.

### 델타

스냅샷에는 직전 송출 이후 상태가 바뀐 플레이어만 담는다.
멍 때리는 사람이 대부분인 공간이라 실효 절감이 크다.

### 상한

| 항목 | 값 | 초과 시 |
|---|---|---|
| 방 정원 | 40명 | 접속 거절 (`error: ROOM_FULL`) |
| 소켓당 메시지 | 30/초 | 1회 경고 후 연결 종료 |
| 페이로드 | 1KB | 연결 종료 |
| 송신 버퍼 | 256KB | 연결 종료 (백프레셔) |
| 채팅 | 40자, 1.5초 쿨다운 | 무시 |

공개 인터넷에 열린 소켓이라 이것들은 선택이 아니다.

### 세션 복구

탭이 백그라운드로 가거나 네트워크가 끊기면 **20초 유예** 후 퇴장 처리한다.
그 안에 같은 `sessionToken`으로 돌아오면 같은 아바타와 위치를 복구한다.

### 관측

`/metrics`로 접속 수, tick 소요 시간, 초당 메시지, 평균 스냅샷 크기를 노출한다.
클라이언트 `F3` 오버레이에 ping과 보간 지연을 띄운다.

## 7. 클라이언트 설계

### 예측과 보간

- **내 캐릭터**: 입력 즉시 로컬에서 `physics.ts`로 이동시킨다. 서버 스냅샷이 오면
  `ack` 이후 입력을 재적용해 보정한다
- **다른 사람**: 100ms 버퍼를 두고 과거 두 스냅샷 사이를 보간한다

일부러 넣는 100ms 지연이다. 10Hz 스냅샷을 그대로 그리면 뚝뚝 끊기기 때문에,
한 프레임 늦게 그리는 대신 부드러움을 얻는다.

### 렌더

Canvas 2D. 타일 32px, 맵 40×30타일(1280×960px). 카메라는 캐릭터를 따라간다.
`render.ts`는 상태를 받아 그리기만 하고 아무것도 바꾸지 않는다.

## 8. 데이터

게임 서버가 자기 데이터를 자기 디스크에 갖는다. 누적 카운터와 잔상은 Next도 블로그도
쓰지 않는 데이터라 Neon까지 갈 이유가 없고, 네트워크 홉이 사라진다.

```sql
CREATE TABLE visitors (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  total INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE traces (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at INTEGER NOT NULL,  -- unix ms
  points BLOB NOT NULL          -- int16 (x,y) 쌍
);
CREATE INDEX traces_created_at ON traces (created_at);
```

- **누적 카운터**: 입장 시 +1. 같은 `sessionToken`은 24시간 내 재입장을 세지 않는다
- **잔상**: 2Hz 다운샘플, 세션당 최대 240포인트(120초). 12시간 지난 행은 주기적으로 삭제
- 하루 한 번 SQLite 파일을 덤프해 백업

## 9. 안전

공개 사이트에 익명 입장과 텍스트 입력을 여는 것이므로 최소한의 방어가 필요하다.

- **닉네임**: 2~10자, 한글·영문·숫자만. **서버에서 검증한다.** 금칙어는
  단순 목록 기반 부분일치 검사로 시작한다. 완벽을 목표로 하지 않고,
  걸리면 입장을 거절하는 대신 다른 닉네임을 요구한다.
  **구현 노트(1단계):** 이 금칙어 목록은 실제로는 `server/`가 아니라
  `shared/nickname.ts`에 있다. 클라이언트가 제출 즉시 같은 규칙으로 피드백을
  줘야 서버 왕복을 기다리지 않고 입력 단계에서 바로 걸러줄 수 있어서다.
  그래서 목록이 브라우저 번들에도 포함되지만, 최종 판정은 여전히 서버가
  같은 함수로 다시 검사해서 내린다 — 클라이언트 검증은 우회 가능한 편의일 뿐이다
- **말풍선**: 40자, 쿨다운 1.5초, 5초 표시 후 사라짐. **서버에 저장하지 않는다**
- **잔상**: 좌표만. 닉네임·텍스트·IP는 저장하지 않는다
- **Origin 검사**: 블로그 도메인에서 온 WS 연결만 허용
- 레이트리밋과 페이로드 상한은 6절 참조

## 10. 인프라

### Oracle Cloud 계정

**되돌릴 수 없는 결정이 하나 있다.** 홈 리전은 가입 시 정해지고 이후 변경할 수 없다.

한국 리전은 둘 다 문제가 있다. 춘천(South Korea North, `ap-chuncheon-1`)은
Always Free A1 provisioning이 불가하고, 서울(South Korea Central, `ap-seoul-1`)은
가입 화면의 홈 리전 목록에 나타나지 않는 사례가 보고된다(2026년 5월).

따라서 **가입 화면에서 실제로 제시되는 목록을 보고 아래 우선순위로 고른다.**

1. 서울이 목록에 있으면 서울
2. 없으면 일본(Osaka `ap-osaka-1` 또는 Tokyo `ap-tokyo-1`).
   서울에서 왕복 30~40ms 수준이라 이 공간에는 문제가 없다.
   클라이언트가 어차피 100ms 보간 버퍼를 두므로 체감 차이가 없다
3. 춘천은 A1을 못 쓰므로 마지막 선택지다

이 결정을 실제로 내리는 시점은 2단계다. 1단계는 `localhost`에서 완결되므로
계정 문제로 진도가 막히지 않는다.

가입 후 **Pay As You Go로 업그레이드한다.** 이유는 두 가지다.

1. `Out of host capacity` 에러가 A1 셰이프에서 매우 흔한데, PAYG는 용량 접근이 열린다
2. 유휴 인스턴스 회수 정책이 Free Tier 계정에만 적용되고 PAYG는 면제다.
   접속자가 없으면 tick도 멈추는 우리 서버는 정확히 회수 대상이다

Always Free 한도 안에서만 리소스를 쓰면 PAYG여도 청구는 0이다.
**예산 알림을 $1에 걸어 과금 사고를 막는다.**

CPU를 일부러 태워 회수를 피하는 방식은 쓰지 않는다. 낭비고 불안정하다.

### 인스턴스

- 셰이프 `VM.Standard.A1.Flex`, 1 OCPU / 6GB (한도 2 OCPU/12GB 안쪽)
- A1 용량을 끝내 못 잡으면 폴백: `VM.Standard.E2.1.Micro` (AMD, 1 OCPU/1GB).
  이 서버에는 충분하다
- ARM64이므로 Node ARM64 이미지를 쓴다

### 배포

- Docker 컨테이너 하나. `docker compose up -d`
- Caddy가 TLS를 자동 발급하고 WSS를 리버스 프록시
- 방화벽은 80/443만 연다 (OCI 보안 목록 + 인스턴스 `iptables` 양쪽 모두)
- systemd로 부팅 시 자동 기동

### 환경변수

| 이름 | 쪽 | 기본값 | 용도 |
|---|---|---|---|
| `LOUNGE_PORT` | 서버 | `8787` | WS 서버가 듣는 포트 |
| `LOUNGE_DB` | 서버 | `./server/lounge.db` | SQLite 파일 경로 |
| `LOUNGE_ALLOWED_ORIGINS` | 서버 | `http://localhost:3000,http://localhost:3001` | WS 연결을 허용할 Origin, 쉼표로 구분 (9절). Origin 헤더가 없는 연결(브라우저가 아닌 클라이언트)은 이 목록과 무관하게 항상 허용한다 |
| `NEXT_PUBLIC_LOUNGE_WS_URL` | 클라이언트 | `ws://localhost:8787` | 브라우저가 접속할 WS 주소 |

**Vercel에 `NEXT_PUBLIC_LOUNGE_WS_URL`을 설정하지 않으면 프로덕션 빌드가
조용히 `ws://localhost:8787`로 접속을 시도한다** — 빌드나 배포가 실패하지
않으므로 브라우저 콘솔을 직접 보기 전까지는 눈치채기 어렵다. 2단계에서
실제 운영 중인 `wss://` 주소로 반드시 바꿔야 한다. `LOUNGE_ALLOWED_ORIGINS`도
그때 블로그의 실제 도메인으로 바꿔야 한다 — 기본값은 localhost만 허용하므로
바꾸지 않으면 운영 도메인에서 오는 연결이 전부 막힌다.

## 12. 단계

각 단계는 그 자체로 완결되고 배포 가능하다.

**1단계 — 로컬에서 도는 방**
`shared/` 3종, 로컬 WS 서버, 닉네임 게이트, 이동·충돌, Canvas 렌더, 오브젝트,
누적 카운터. Oracle 없이 `localhost`에서 완결된다.

여기서 "오브젝트"는 **맵에 놓이고, 충돌하고, 조사하면 설명이 뜨는 것**까지다.
라디오가 실제 헤드라인을 읽거나 화분이 자라는 등 오브젝트별 고유 동작은 4단계다.
클라이언트 예측·보간도 3단계이므로, 1단계는 서버 스냅샷 위치를 **그대로** 그린다.
10Hz라 눈에 띄게 끊기는데 이것이 의도된 기준선이다. 3단계의 개선을 이 상태와
비교해서 측정한다.

**2단계 — 인터넷에 올리기**
Oracle 계정(서울·PAYG), 인스턴스, Docker, Caddy, 도메인, 방화벽.
실제로 다른 사람이 접속된다.

**3단계 — 네트워킹 본론**
클라이언트 예측·보정, 원격 보간, 델타 인코딩, 바이너리 스냅샷, 레이트리밋,
백프레셔, 세션 복구, `/metrics`, F3 오버레이. **전후 대역폭을 측정해 기록한다.**

**1단계 기준선 (측정 완료, 2026-10-02):** 브라우저 없이 `ws` 클라이언트로 직접
측정했다. `tsx server/index.ts`로 서버만 `localhost:8787`에 띄우고, 스크립트로
20명(`ROOM_CAPACITY`의 절반)을 접속시켰다 — 그중 10명은 접속 직후 한 방향으로
계속 걷고, 10명은 입력을 전혀 보내지 않는다("멍 때리는 사람이 대부분"이라는
실제 사용 패턴). 접속·welcome·join 브로드캐스트가 가라앉도록 3초를 기다린
뒤, 10초 구간을 고정해 각 클라이언트가 **받는** 트래픽만 집계했다.

| 지표 | 값 |
|---|---|
| 클라이언트당 bytes/s | 21,012.6 B/s (약 20.5 KiB/s) — 20명 전원 동일 |
| 클라이언트당 messages/s | 9.90 msg/s (10초 창에 스냅샷 99개 수신. `SNAPSHOT_HZ`=10이고 서버 tick과 측정 창의 경계가 딱 맞아떨어지지 않아 생기는 ±1 창 경계 오차로, 실제 송출 주기 오차가 아니다) |
| 평균 스냅샷 크기 | 2,122.5 B (JSON, 플레이어 20명 전체를 매번 통째로 담는다) |

전원이 20명 그대로 있는 한, 멍 때리는 쪽이 늘어도 이 숫자는 거의 그대로다 —
1단계는 델타가 없어서 스냅샷이 "변경된 사람만"이 아니라 항상 전원을 담기
때문이다. 3단계에서 델타+바이너리 인코딩을 넣은 뒤 **같은 인원(20명, 같은
절반-이동/절반-유휴 패턴)으로 다시 재서 이 표와 나란히 비교한다.**

**4단계 — 공간 채우기**
잔상, NPC, 라디오, 모닥불, 책장, 화분, 이모트.

1단계가 Oracle과 분리되어 있어서, 가입이나 용량 확보에서 막혀도 진도가 멈추지 않는다.

**각 단계는 자기 구현 계획을 따로 갖는다.** 네 단계를 한 계획에 묶기에는 크고,
1단계 결과를 보고 나서야 3단계의 측정 대상이 정해진다. 첫 구현 계획은 1단계만
대상으로 한다.

## 13. 성공 기준

- 닉네임만 넣고 3초 안에 입장한다
- 두 브라우저에서 동시 접속했을 때 상대 캐릭터가 끊김 없이 부드럽게 움직인다
- 아무도 없는 시간에 들어와도 잔상과 NPC와 오브젝트 덕분에 빈 방으로 느껴지지 않는다
- 멍 때리며 가만히 있는 동안 클라이언트가 보내는 메시지가 0이다
- 탭을 전환했다 돌아와도 같은 아바타로 이어진다.
  **1단계 기준 미충족 (알려진 범위):** `server/room.ts`의 `join`은 재입장마다
  `hue`를 다시 무작위로 뽑는다. 같은 `sessionToken`으로 돌아오면 닉네임과
  (재접속 유예 안이라면) 위치는 이어지지만 색은 매번 바뀐다. 세션별로 `hue`를
  저장해 복원하는 일은 3단계 세션 복구(`REJOIN_GRACE`, 끊김 유예) 범위에서
  같이 다룬다 — 지금은 충족된 것처럼 두지 않고 알려진 간극으로 남겨둔다
- 3단계 전후 대역폭 절감률을 숫자로 말할 수 있다
