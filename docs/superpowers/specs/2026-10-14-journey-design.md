# 여정(Journey) 설계

2026-10-14

## 1. 개요

블로그의 프로젝트 7개를 하나의 3D 공간으로 보여주는 포트폴리오 페이지 `/journey`.
콘셉트는 **A Journey Through Code**. 방문자가 스크롤하면 카메라가 2023년의 첫 프로젝트에서
현재의 PiCKCARE까지 회랑을 따라 걸어간다.

목표는 두 가지다.

- **이직·포트폴리오**: 채용 담당자에게 성장 과정과 실제 제품 역량이 남는 인상
- **공부**: three.js, 셰이더, 스크롤 연출을 최고 완성도로 직접 만드는 경험

세 요소를 역할별로 나눠 결합한다. 비중은 대략 6 : 2.5 : 1.5다.

| 요소 | 역할 | 보여줄 가치 |
|---|---|---|
| 시간의 회랑 | 공간 전체 구조. 스크롤하면 과거에서 현재로 이동 | 개발자로서의 성장 과정 |
| 미술관 전시실 | 회랑 중간의 전시 구역과 상세 정보 | 실제 제품을 설계하고 구현한 역량 |
| 떠 있는 오브젝트 | 프로젝트의 성격을 해석한 추상 조형물 | 제품의 본질을 시각적으로 해석하는 능력 |

원칙:

- **스크롤은 서사, 클릭은 탐색.** 스크롤만으로 처음부터 끝까지 이어진다. 상세를 보려고
  클릭하거나 카메라를 조작하도록 강요하지 않는다.
- **오브젝트보다 실제 성과가 우선.** 3D는 시선을 끄는 역할이다. 상세 화면에는 제품 화면,
  담당 범위, 기술적 의사결정, 해결한 문제를 보여준다.
- **3D는 공간과 카메라만.** 글은 처음부터 끝까지 진짜 HTML이다.
- **부드러움은 필수 조건이다.** 스크롤과 카메라가 매 프레임 끊김 없이 따라가야 한다.
  화질보다 부드러움이 먼저다.

### 비목표

- 서버, 데이터베이스, 외부 API. 정적 호스팅만으로 동작한다.
- 외부 3D 모델 파일. 모든 형태는 코드로 만든다.
- 블로그 글 디자인 통일. 각 글의 지금 모양을 그대로 유지한다.
- 블로그 글 목록(`src/data/posts.ts`) 변경
- 이력서 PDF
- 다국어

## 3. 시각 언어

### 렌더 단계: 청사진 → 클레이 → 완성품

3D 렌더링이 실제로 거치는 단계(와이어프레임 → 셰이딩 → 재질)를 개발자의 성장에 겹친다.

- 1막: 선만 있는 와이어프레임. 짙은 남색 배경, 빛나는 하늘색 선, 바닥 격자.
- 2막: 색 없는 클레이. 중립 회색, 부드러운 그림자의 스튜디오 조명.
- 3막: 재질과 색이 다 입혀진 공간. 따뜻한 주광, 환경 반사, 유리.

**렌더 단계는 공간 위치의 함수다.** `stage(z)`는 회랑의 앞뒤 위치를 받아 0(와이어) ~
1(클레이) ~ 2(완성)를 돌려준다. 회랑과 오브젝트의 셰이더가 이 함수를 함께 쓴다
(`MeshStandardMaterial`에 `onBeforeCompile`로 주입). 그래서 "오브젝트는 자기가 속한 막의
렌더 단계를 따른다"는 규칙이 저절로 지켜진다.

막 경계에는 **렌더 전환선**이 있다. 전환 구간에서는 노이즈 경계를 따라 다음 단계가 섞여
들어와, 앞쪽 공간이 "렌더링되어 가는" 것처럼 보인다. 경계에는 얇게 빛나는 선이 흐른다.

조명, 안개, 배경색은 카메라 위치에 따라 매 프레임 보간한다. 3막의 환경 반사는 이미지
파일 없이 drei `Lightformer`로 만든다.

후처리는 최소한으로 한다. 블룸(1막 선과 전환선), 안티에일리어싱, 약한 비네트만 쓴다.
성능이 떨어지면 블룸부터 끈다.

제품 스크린샷은 3D 공간에 걸지 않는다. 클레이 공간에 컬러 스크린샷이 걸리면 렌더 단계
비유가 깨진다. 스크린샷은 HTML 패널과 상세 화면에만 쓴다.

### 프로젝트 오브젝트: 추상 조형형

상징의 실루엣은 남기되 원판, 링, 판, 구 같은 기본 도형으로 해체한다. 7개가 같은 도형
어휘를 써서 한 세트로 보이고, 분해·결합 애니메이션으로 프로젝트를 이루는 부분들을 보여준다.

| 프로젝트 | 본질 | 오브젝트 |
|---|---|---|
| 코코아톡 | 대화 | 겹쳐 떠 있는 둥근 판 두세 장이 번갈아 떠오름 (말풍선) |
| Todo App | 할 일 목록 | 쌓인 얇은 판이 하나씩 옆으로 밀려나며 완료됨 |
| EUTCHA | 영화 | 창이 뚫린 띠가 링을 따라 천천히 감김 (필름) |
| Stock2U | 위치 + 재고 | 쌓인 상자 위로 떠서 위아래로 움직이는 핀 (원뿔 + 구) |
| Tix2U | 티켓 | 절취선에서 갈라지는 두 판, 사이로 흩어지는 작은 조각 |
| PFPlay | 음악 + 아바타 | 층으로 분리돼 도는 원판, 궤도를 도는 아바타 구 |

상호작용: 마우스를 올리면 살짝 떠오르고 커서가 바뀐다. 클릭하면 상세 화면이 열린다.

### 스크롤과 렌더링

역할 분담:

- **브라우저 기본 스크롤**이 스크롤 위치의 단일 원천이다. 접근성, 찾기, 검색, 2D 전환이
  그대로 유지된다.
- **Lenis**가 휠과 트랙패드 스크롤에 관성을 준다. 터치 기기에서는 끄고 OS 기본 관성을 쓴다.
- **GSAP ScrollTrigger**가 구간 연출을 맡는다. 고정(pin), 막 전환, 패널 등장 타이밍을
  `scrub`으로 스크롤 진행률에 묶는다.
- **카메라**는 스크롤에서 목표 위치를 계산하고, 매 프레임 감쇠로 따라간다. 감쇠는 프레임
  간격(delta)으로 계산해 60Hz와 120Hz에서 같은 속도로 움직인다.

**시계 하나.** Lenis, GSAP, R3F가 각자 requestAnimationFrame을 돌면 한 프레임씩 어긋나며
떨린다. GSAP ticker 하나가 매 프레임 다음 순서로 호출한다.

1. `lenis.raf(time)`
2. `ScrollTrigger.update()`
3. R3F `advance(time)` (Canvas는 `frameloop="never"`)

**React는 스크롤 중에 다시 렌더링하지 않는다.** ScrollTrigger는 `scrollState`(가변 객체)에
기록하고, 카메라와 오브젝트는 프레임 콜백에서 그 값을 읽는다.

**적응형 품질.** drei `PerformanceMonitor`로 프레임이 떨어지면 해상도 배율과 후처리를
낮춘다.

### 사이트 공통 요소 변경

- `Background3D`는 `/journey`에서 렌더링하지 않는다. WebGL 화면과 애니메이션 루프가 둘이
  되면 시계 하나 원칙이 깨진다. `usePathname`으로 확인해 `null`을 반환한다.
- 헤더는 유지하되 `/journey`에서는 `backdrop-blur`를 끈다. 움직이는 캔버스 위의 흐림은 매
  프레임 GPU 재합성을 일으킨다.

### 의존성

| 패키지 | 구분 | 용도 |
|---|---|---|
| `gsap` | 런타임 | ScrollTrigger, ticker |
| `lenis` | 런타임 | 부드러운 스크롤 |
| `@playwright/test` | 개발 | 화면 비교, 동작 테스트, 스크린샷 촬영, 성능 측정 |
| `@axe-core/playwright` | 개발 | 접근성 검사 |

버전은 구현 시점에 2주 이상 지난 안정 버전으로 정확히 고정한다. three, R3F, drei,
postprocessing, maath는 이미 설치돼 있다.

## 5. 기기 대응

| 단계 | 대상 | 내용 |
|---|---|---|
| 3D 전체 | WebGL2가 되고 `(pointer: fine)`인 기기 (데스크톱·노트북) | 전체 연출 |
| 3D 경량 | WebGL2가 되고 `(pointer: coarse)`인 기기 (휴대폰·태블릿) | 해상도 배율 최대 1.5, 블룸 끔, 유리를 가벼운 재질로 교체. 회랑·렌더 단계·오브젝트 연출은 유지 |
| 2D | WebGL2 미지원, `navigator.deviceMemory` 2 이하, `navigator.connection.saveData` 켜짐 | 세로 타임라인 |

`deviceMemory`와 `connection`은 Safari에 없다. 값이 없으면 판정에 쓰지 않는다(2D로 보내지
않는다).

- **실행 중 강등**: 3D 전체에서 45fps 아래로 2초 넘게 떨어지면 3D 경량으로, 3D 경량에서
  24fps 아래로 2초 넘게 떨어지면 2D로 내린다. 지금 보던 정류장은 유지한다. 셰이더 사전
  컴파일이 끝나기 전 프레임은 세지 않는다. WebGL 컨텍스트를 잃어도 2D로 내린다.
- **수동 전환**: 구석에 "2D로 보기 / 3D로 보기" 버튼. 선택은 `localStorage`에 기억한다.
- **움직임 줄이기**(`prefers-reduced-motion`): 3D는 유지하되 Lenis 관성, 오브젝트 자동 회전,
  긴 카메라 이동을 끈다.

### 2D 레이아웃

- 같은 본문 HTML을 세로 타임라인으로 보여준다. 왼쪽 세로선이 막마다 청사진 파랑 → 클레이
  회색 → 완성 색으로 바뀐다.
- 오브젝트는 정지 이미지로 보여준다. 3D 오브젝트를 스크립트로 렌더링해 WebP로 저장한
  스냅샷(`public/journey/objects/<slug>.webp`)이다. 원본이 하나라 2D와 3D가 어긋나지 않는다.
  스냅샷용 페이지 `/journey/snapshot`은 개발 모드에서만 열리고 운영에서는 `notFound()`다.
- 상세는 휴대폰에서 아래에서 올라오는 전체 화면 시트로 열린다.
- 등장 효과는 기존 `FadeIn`을 쓴다.

### 로딩

- HTML 본문은 서버에서 렌더링되어 3D보다 먼저 보인다.
- 3D 코드는 `/journey`에서만, 기기 판별이 끝난 뒤 `next/dynamic`(`ssr: false`)으로 불러온다.
- **셰이더 사전 컴파일**: 세 렌더 단계의 모든 재질을 입구 화면에서 `gl.compile`로 미리
  컴파일한 뒤 스크롤을 켠다. 첫 스크롤에서 셰이더 컴파일로 끊기는 것을 막는다.

type Inline = string; // **굵게**, [텍스트](주소) 지원

interface ProjectLink { label: string; href: string }
interface Screen { src: string; alt: string; width: number; height: number }

interface ProjectBase {
  slug: string;
  title: string;
  period: string;        // "2023.11.17 ~ 2023.12.22"
  team: string;          // "Team Project (FE 2명)"
  summary: Inline;
  stack: string[];
  links: ProjectLink[];
  screens: Screen[];     // 첫 장이 블로그 썸네일
}

interface StandardProject extends ProjectBase {
  kind: "standard";
  overview: Inline[];
  overviewCallout?: { title: string; text?: Inline; items?: Inline[] };
  roleIntro?: Inline;
  role?: Inline[] | { title: string; items: Inline[] }[];   // Tix2U는 소제목 묶음
  extraSections?: { title: string; items: Inline[] }[];     // EUTCHA "기술 스택 및 규칙"

  note?: { title: string; text: Inline };
}

interface Case { title: string; problem: Inline[]; solution: Inline[]; result: Inline[] }
interface Repo { name: string; tagline: Inline; stack: string[]; cases: Case[]; screens: Screen[] }

interface ReposProject extends ProjectBase {

  repos: Repo[];
  closing: Inline[];
}

type Project = StandardProject | ReposProject;

### 원칙

- **내용만 담는다.** 참고 사항 상자 색(주황·빨강), 글마다 다른 본문 색 지정 같은 모양은 각

  바꾼다. 내부 주소는 `next/link`, 외부 주소는 `<a target="_blank" rel="noreferrer">`다.
  페이지마다 `<strong>`에 붙은 클래스를 받아 지금과 같은 마크업을 만든다.
- 원문은 오탈자까지 그대로 옮긴다. `pickcare/page.tsx`의 "작업량이 습니다"도 사용자
  결정으로 그대로 둔다.
- `src/data/posts.ts`는 바꾸지 않는다. 목록용 설명·태그가 본문과 미묘하게 달라 합치면 목록

## 8. 테스트

### 1. 단위 (vitest)

- `timeline.ts`: 정류장 길이 합, 진행률 증가 시 카메라가 경로를 따라 앞으로만 감, `stage(z)`가
  막 경계와 전환 구간에서 정확한 값, 모든 프로젝트에 정류장 존재, 프로젝트 정류장이 종료일
  순서
- `damp.ts`: 같은 시간이 흐르면 60Hz와 120Hz에서 결과가 오차 안에서 같음
- `capability.ts`: 기기 조건 조합별 단계 판정
- `inline.tsx`: 굵게, 내부·외부 링크, 섞인 문장, 짝이 안 맞는 기호, strong 클래스.
  `react-dom/server`로 렌더해 jsdom 없이 검사
- 데이터 무결성: 필수 필드, slug 중복 없음, 선언한 이미지 파일 존재와 크기 일치, 2D 스냅샷
  7장 존재

순수 함수 모듈은 테스트를 먼저 쓴다.

### 2. 화면 비교 (Playwright, 1단계 통과 조건)

블로그 프로젝트 글 7개 × 데스크톱(1280px)·모바일(390px)을 리팩터링 전 기준 이미지와
픽셀 단위로 비교한다. `Background3D`는 무작위로 움직이므로 촬영 시 숨기고, `FadeIn`
애니메이션이 끝난 뒤 찍는다.

### 3. 동작 (Playwright, `/journey`)

- 3D 모드: 콘솔 에러 없음, 끝까지 스크롤하면 엔딩 도달, "자세히 보기"로 패널 열림, ESC로
  닫힘, 포커스 복귀, `/journey#pfplay` 진입 시 패널 열림, 뒤로 가기로 닫힘
- 2D 모드(수동 전환으로 강제): 모든 본문과 상세 동작
- 움직임 줄이기 에뮬레이션: Lenis 꺼짐
- 접근성(`@axe-core/playwright`): 3D, 2D, 패널 열린 상태 각각

### 4. 부드러움 측정

헤드리스 브라우저는 소프트웨어 렌더링이라 실제 기기와 숫자가 다르다. 그래서 실제 기기에서
잰다.

- `npm run perf:journey`: GPU를 쓰는 실제 Chrome 창에서 회랑 전체를 정해진 속도로
  스크롤하고, 프레임 간격의 평균 · 95번째 백분위 · 50ms 초과 개수를 출력한다.
- 휴대폰은 실제 기기에서 `?debug=perf` 오버레이(fps, 프레임 시간, 드로우 콜)로 확인한다.
- 결과는 완료 보고에 숫자로 남긴다.

## 9. 결정 기록

| 결정 | 고른 것 | 고르지 않은 것과 이유 |
|---|---|---|
| 공간 콘셉트 | 회랑 + 전시실 + 오브젝트 결합 | 셋 중 하나만 쓰면 서사·정보·차별화 중 하나가 빠진다 |
| 공간 배분 | 3막 구성 | 균등 배치는 경력의 깊이가 묻히고, 주요 프로젝트만 두면 성장 축이 약하다 |
| 상세 내용 출처 | 블로그 글을 데이터로 분리해 공유 | 갤러리 전용 요약은 내용이 두 벌이 된다 |
| 위치 | 독립 주소 `/journey` | Playground 하위는 실험작처럼 보이고, 홈 교체는 블로그 성격을 해친다 |
| 블로그 디자인 | 각 글 모양 유지 | 공통 템플릿은 사용자가 원하지 않음 |
| 엔딩 | 연락처 + 최근 글, PDF 없음 | 사용자 결정 |
| 시각 방향 | 청사진 → 클레이 → 완성품 | 새벽→아침은 흔한 비유, 화이트 미술관은 공간이 성장을 말하지 못한다 |
| 오브젝트 | 추상 조형형 | 상징형은 클립아트처럼 보이고, 데이터 생성형은 무슨 서비스인지 안 읽힌다 |
| 스크롤 | 기본 스크롤 + Lenis + ScrollTrigger + 시계 하나 | drei ScrollControls는 스크롤을 가로채 접근성과 2D 전환이 약하다 |
| 휴대폰 | 3D 경량으로 시작, 실행 중 강등 | 처음부터 2D면 휴대폰으로 연 채용 담당자가 첫인상을 놓친다 |
